# Test the numbers students act on, and run the suite on Postgres

**Branch** `feature/test-coverage-and-postgres-ci` → `development`
**Version** 0.5.0

---

## Why

Two gaps, both of the kind that stay invisible until they cost someone a paper.

**The backend produced numbers nothing asserted.** `ProgressTracker`,
`DailyPlanner` and `MockAnalyser` were exercised only through API tests, which
check that a response has the right shape. A readiness score of 43% looks
exactly as plausible as a readiness score of 61%; end-to-end coverage cannot
tell them apart.

**The SPA had no tests at all.** Including the mock exam timer, and the
entitlement locks — where what matters is the *failure* mode. A lock that opens
while its request is in flight, or opens when the request 500s, leaks the paid
product and no amount of manual clicking would reliably catch it.

**CI never ran the suite on a real database.** The Postgres job migrated and
seeded, then stopped. SQLite forgives SQL that Postgres rejects, so the divergence
only ever surfaced by hand.

## Bugs this found

Writing the tests was not a formality.

**1. `DailyPlanner` could not find the plan it had just written.**

```php
// Before: string equality against a `date` column.
StudyPlan::firstOrNew([... 'plan_date' => $date->toDateString()]);
// After
->whereDate('plan_date', $date->toDateString())
```

Postgres normalises the column so the comparison happened to work. SQLite stored
`2026-08-03 00:00:00`, the lookup missed, and the second call for the same day
tried to insert a duplicate and hit the unique constraint.

**2. `RolesTableSeeder` deleted every row before reinserting** — but
`plans.role_id` references `roles`. Re-seeding therefore fails on any database
that enforces foreign keys, which is to say on production. Now an idempotent
upsert.

**3–4. Three inherited Wave tests passed on SQLite by accident.**
`PlanSwitchingTest` and `StripeWebhookTest` ran `migrate:fresh` inside an open
transaction; `UsernameUpdateTest` read `User::limit(2)` when the seed creates
one user, and only worked because an earlier file left a factory user behind.

**5. The mock exam clock ran slow.** `submit` depended on the object
`useMutation` returns, which is new every render, so each re-render restarted
the countdown's one-second timeout. Students who kept answering watched a clock
that fell behind the server's deadline. The countdown now derives from a
wall-clock deadline. Found only once CI ran the timer tests on a slower Linux
runner.

**6. CI could not pass from a clean checkout** — a macOS-written npm lock
missing Linux optional packages, a PHP 8.2 matrix entry PHPUnit 12 cannot
install on, and Wave page tests that needed a local Vite build. Fixed with a
Linux-generated lock, PHP 8.3 / 8.4, and `withoutVite()`.

## Notes for review

- `tests/bootstrap.php` returns early unless the driver is SQLite. Against any
  other connection the caller owns the schema — the CI job migrates and seeds
  before PHPUnit starts, for the same reason the SQLite fixture exists: Wave
  reads its theme and settings during service-provider boot.
- `phpunit.xml` sets `DB_CONNECTION` **without** `force`, so a shell-supplied
  value wins. That is what makes `DB_CONNECTION=pgsql php artisan test` work.
- Postgres env vars are set at job level rather than per step because GitHub
  Actions does not support YAML anchors.

function of `past_questions`, which is still representative sample data rather
than verified BCS papers.
